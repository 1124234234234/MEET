一、项目概述

1.1 项目背景

会议室场景下的会议内容需要可追溯、可核查：会议讲了什么、谁讲的、是否传达了必须传达的
合规要点、有没有出现不当或消极表述。人工整理纪要成本高且容易遗漏。本系统对会议音频做
自动转写、说话人分离、文本结构化与合规比对，输出可直接归档的会议记录与合规报告。

1.2 核心能力

  1. 语音转写：会议音频转成带标点、带时间戳的文字
  2. 说话人分离：区分不同发言者，得到「谁在什么时候说了什么」
  3. 音频预处理：降噪、回声抑制、语音增强
  4. 文本分析：关键词、主题、摘要、情绪、待办事项、决议结论
  5. 合规比对：与知识库做语义相似度比对、逐条核查必传要点、识别遗漏与风险、
     生成 0-100 分评分、标记风险内容的音视频时间节点
  6. 实时转写：浏览器麦克风边录边转，会议中实时给出合规提示
  7. 数据管理：结构化会议记录入库、多条件查询、HTML 报表导出
  8. 第三方集成：POST /api/v1/transcribe 供外部系统调用

1.3 技术亮点

  - 全离线：所有模型从项目 models/ 目录加载，运行期不访问外网，也不依赖显卡
  - 中文优先：识别用 FunASR paraformer-large（而非 Whisper），自带标点恢复与热词增强
  - 识别效率：CPU 实时率约 0.1，比 Whisper medium 快一个数量级
  - 说话人分离不依赖麦克风阵列，也不需要预先知道人数
  - 量化可验证：字错误率、说话人混淆率等指标有脚本化评测，可复现

2.3 核心流程

2.3.1 上传音频分析流程（POST /api/meetings）

  1. 保存上传文件，创建状态为 processing 的会议记录，立即返回 meeting_id
  2. 后台线程执行分析：
       a. 音频预处理（降噪、带通、语音增强、归一化）
       b. 语音识别（fsmn-vad 细粒度分段 → 逐段识别 → ct-punc 恢复标点）
       c. 说话人分离（在预处理后的音频上做声纹聚类）
       d. 说话人归属（按时间重叠最大把说话人写到每个分句上）
       e. 关键词、主题、摘要、情绪、待办事项、决议结论
       f. 合规比对（语义相似度、要点覆盖、风险识别、评分）
       g. 转写分句与合规报告入库，会议状态置为 finished
  3. 全程通过 Socket.IO analysis_progress 推送进度，也可用
     GET /api/meetings/{id}/progress 轮询

2.3.2 实时转写流程（HTTP 分块上传，页面使用）

  1. 客户端 POST /api/realtime/start（上报实际采样率、会议标题、语言、热词）
  2. 浏览器采集 PCM（16bit 单声道），每 500ms 汇总一块 POST /api/realtime/chunk
  3. 服务端按静音断句累积（静音 0.35s 或缓冲满 8s 触发一次识别），
     调用识别引擎（引擎内部再做 VAD 分段），返回分句文本与时间戳
  4. 每段结果同时做实时合规比对，命中风险/覆盖要点时随结果一并返回
  5. 客户端 POST /api/realtime/stop → 保存完整音频 → 复用已有转写做完整分析
     （含说话人分离与合规评分）→ 入库
  6. 客户端轮询 GET /api/realtime/result/{session_id} 获取进度与最终结果

  为什么页面不再用 Socket.IO：socket.io 的浏览器客户端只能从 CDN 加载，
  而本系统要求离线可用；加载失败会让整个实时功能点了没反应。HTTP 通道只用
  浏览器自带的 getUserMedia / AudioContext / fetch，零外部依赖。
  服务端仍保留 Socket.IO 事件（transport 层共享同一个转写会话实现），
  供已有第三方客户端继续使用。

2.3.3 合规检查流程

  1. 从知识库取启用条目，按类型分为政策、必传要点、风险关键词
  2. 语义相似度：对每条政策计算与转写文本的句向量余弦相似度，取最相关的一条计分
  3. 要点覆盖：选定相关政策对应的必传要点模板，逐条判定是否被覆盖
     （要点文本或同名关键词出现在转写中即视为覆盖），未覆盖的记为遗漏
  4. 风险识别：风险关键词命中（排除否定语境）+ 语义风险句式（表述不当、消极负面）
  5. 评分：四项加权求和，并生成改进建议
  6. 时间定位：风险与要点均记录命中句的起止时间，用于回溯音视频

四、核心功能模块详解

4.1 音频 I/O 模块（audio_io.py）

  统一音频读写：soundfile 优先（wav/flac/ogg），mp3/m4a 等格式回退到内置
  imageio-ffmpeg 解码（不依赖系统 PATH 中的 ffmpeg）；重采样用
  scipy.resample_poly 实现，避免 librosa/numba 的额外开销。
  所有模块共用，不再各自实现一份。

4.2 模型装载中心（model_registry.py）

  设计要点：
  1. 离线优先：按关键字在 models/ 下查找本地模型目录（兼容 modelscope 的
     snapshots/master 结构），本地存在时强制 local_files_only，
     不在离线环境下向 HuggingFace 反复发请求重试；
  2. 全局单例：语音识别流水线、VAD、句向量模型各只加载一次；
     句向量模型由 text_analyzer 与 compliance_checker 共享
     （旧实现各自加载一份，多占约 200MB 内存）；
  3. 可降级：模型缺失时返回 None，由调用方走降级分支；
  4. 状态可查：status() 返回各模型是否就位，供健康检查与启动器使用。

4.3 音频预处理模块（audio_preprocessor.py）

  **按信噪比自适应选择处理强度**（不是一刀切跑全套）：

  先估计输入音频的信噪比（噪声底 = 能量最低 10% 帧的平均功率），再分两档：
    - 估计 SNR >= 20dB（干净）→ 轻度：80-7000Hz 四阶带通 + RMS 归一化到 -20dB
    - 估计 SNR <  20dB（含噪）→ 降噪：noisereduce 谱减法 + RMS 归一化

  这个阈值与两档选择都来自实测（gt_meeting / gt_2spk 带标注音频）：

    处理方式                干净音频 CER        加噪音频 CER(SNR10dB)
    不处理                  4.11% / 4.55%       43.15% / 45.45%
    一整套（旧实现）        23.29% / 8.59%      39.04% / 23.23%
    轻度：带通+归一化       2.05% / 4.55%       48.63% / 42.42%
    降噪+归一化             11.64% / 9.09%      34.25% / 21.72%

  结论：旧实现「不管什么音频都降噪+增强」在干净音频上把 CER 拉高 5 倍
  （2 人对话 4.11% → 23.29%），因为谱减与谱增益会削掉清音/辅音；而在含噪音频上
  降噪确实能把 CER 从 43% 救到 34%。交叉点实测在 20dB 附近。

  「语音增强（MMSE）」与「降噪后再带通」保留为可用能力但默认不放入链路：
  实测没有额外收益（10dB 下 34.25% vs 36.99%），却增加耗时。

  辅助功能：detect_speech_segments（能量 VAD）、format_time、
  get_audio_quality_report（基于噪声底估计 SNR，对比处理前后；SNR 估计经合成加噪样本
  验证：真实 20/15/10/5dB → 估计 19.85/14.88/9.94/5.14dB）。

4.4 语音识别模块（asr_engine.py）

  统一引擎，三种实现同一接口：

  1. FunASREngine（主）：paraformer-large + ct-punc
       - 分段：调用本地 fsmn-vad，参数取 max_end_silence_time=300ms、
         max_single_segment_time=15s，得到句子级分段
         （默认 800ms 会把整段连续语音并成一片）
       - 识别：把各段组成一批一次性送入模型，返回每段的文本与精确时间戳
       - 标点：由 ct-punc 恢复，不再用正则猜标点
       - 热词：支持 hotword 参数，提升行业术语识别率
  2. WhisperEngine（备）：FunASR 不可用时接管，转写后做繁简转换，
     返回结构完全一致
  3. RemoteVoiceEngine（边缘部署）：配置 VOICE_API_URL 后把识别请求转发到远端
     voice-api，本机不加载识别模型

  对外统一返回：{'text', 'segments': [{'start','end','text','confidence'}],
                 'language', 'engine'}

4.5 说话人分离模块（speaker_diarization.py）

  解决「谁在什么时候说话」，不依赖麦克风阵列、不需要预先知道人数。

  4.5.1 处理步骤

  1. 语音区间：复用 asr_engine.detect_speech_regions（FunASR VAD，能量 VAD 兜底），
     并做过短片段合并与超长片段切分
  2. 特征：MFCC 1-19 阶（去掉 0 阶，它只反映音量）+ 一阶/二阶差分，
     整体做倒谱均值方差归一化（CMVN）抑制信道差异
  3. 窗口嵌入：1.5s 窗、0.5s 步长，窗口内取「均值 + 标准差」拼接，
     L2 归一化后作为该窗口的说话人嵌入
  4. 聚类：余弦距离 + 凝聚层次聚类（average linkage）
  5. 人数选择：余弦轮廓系数在 2..6 之间选优，得分接近（<0.02）时取更少的说话人；
     轮廓系数整体过低时判定为单人发言
  6. 碎片簇归并：把「碎片簇」并入最近簇（判据见 4.5.2）
  7. 后处理：中值滤波平滑标签、过短说话人段吸收、按首次发言顺序重编号为 SPEAKER_00/01/…

  4.5.2 两个关键判据都来自实测

  （1）特征选择（同说话人 / 不同说话人窗口的余弦距离）：

      特征              同说话人      不同说话人    分离错误率
      对数梅尔谱        0.145         0.199         约 24%
      MFCC（本方案）    0.047         0.099         约 8.6%

  梅尔谱保留完整能量分布，受「说了什么」影响大；倒谱系数描述声道形状（共振峰），
  对内容变化更稳健。因此选用 MFCC，并把窗口从旧的 32ms 帧拉长到 1.5s。

  （2）碎片簇判据。错误多出来的「说话人」形态高度一致，四个样本实测：

      样本            真实人数 估计k  多余簇的形态
      3人合成会议      3       4      1 个窗口、1.05s、1 个连续段、占比 1.1%
      2人合成对话      2       2      （无多余簇：两簇各占 64.7% / 35.3%）
      真实单侧通话1    1       2      2 个窗口、1.70s、1 个连续段、占比 3.7%
      真实单侧通话2    1       2      2 个窗口、1.68s、1 个连续段、占比 2.0%

  真实说话人的簇最少也有 18 个窗口、35% 占比。判据取「窗口数 <= 2 且时间跨度 < 2.5s
  且只含 1 个连续段 → 视为碎片，并入最近簇」。这里不再设「至少保留 N 个说话人」的下限：
  曾经用过这个下限，结果单说话人录音被拆成 2 人（真实通话1/2 就是这样）。

  4.5.3 说话人归属

  assign_speakers_to_segments() 按「时间重叠最大」把说话人写到识别分句上；
  无重叠时退回时间最近的时间段。旧实现用「分句起点落在哪个区间」判断，
  边界稍有偏差就会张冠李戴。

  4.5.4 质量评估

  evaluate(reference, hypothesis)：以 10ms 为粒度建立混淆矩阵，用匈牙利算法求
  「识别标签 → 真实说话人」的最优置换，输出逐帧正确率、混淆率（1 - 正确率）
  与说话人数量误差。这是需求中「说话人日志混淆率 < 5%」指标的评测函数。

  4.5.5 可选增强

  配置 ENABLE_PYANNOTE=1 且提供 HF_TOKEN 时改用 pyannote 声纹模型
  （其说话人嵌入即 ECAPA-TDNN 一类模型）。默认关闭：离线环境下其模型无法下载，
  开启只会长时间重试。

4.6 文本分析模块（text_analyzer.py）

  4.6.1 关键词提取（extract_keywords）
    jieba 词性标注只保留名词/动词/专有名词等实词 → 通用停用词 + 领域停用词
    + 长度过滤 → TF-IDF（IDF 按句分布估计）→ 词性加权
    （专有名词 1.5、名词 1.3、动词 1.1）→ 取 Top N

  4.6.2 主题分析（analyze_topic）
    本地 bge-small-zh-v1.5 计算文本与 16 个候选主题的余弦相似度（权重 0.7），
    叠加主题词库命中率（权重 0.3）；语义模型不可用时降级为纯关键词匹配。
    模型加载放在独立线程并设超时，避免首次加载拖慢整条分析流程。

  4.6.3 摘要生成（generate_summary）
    1. 智能分句（处理无标点或标点不全的文本）
    2. TextRank 抽取关键句作为保底结果
    3. 大模型生成：Qwen2.5-1.5B-Instruct 优先，失败或疑似幻觉时退回 mT5，
       再退回抽取式摘要
       - 输入按时间轴均匀抽样，保证覆盖整场会议（旧实现只取前 3000 字，
         一小时会议只能总结前二十分钟）
       - 贪心解码（num_beams=1、do_sample=False）：CPU 上速度提升约 3 倍，
         摘要这类偏「忠实复述」的任务质量几乎无损
       - 幻觉检测两道：① 新闻式模板词（「报道/记者/证监会/《》/X月X日」）；
         ② 「3 字以上实体有多少不在原文」的粗筛，且**只在该类实体不少于 8 个时启用**。
         抽象式摘要必然引入原文没有的表达，样本太少时比例不可靠：
         实测一段 166 字通话，摘要只有 3 个长实体且都不在原文，ratio 冲到 1.0，
         把一份完全正确的摘要误判成幻觉、退回粗糙的抽取式拼接
       - 第三人称改写只做**短语级**替换（「我认为」→「有观点认为」）。
         旧实现把裸代词「我/我们/咱们/大家」无条件全局替换，产生
         「参会人员这个方案还是比较实在的」这类语义错误句
    4. 后处理：口语词清理、重复内容合并、长度截断

  4.6.4 情绪分析（analyze_sentiment）
    规则词典（带否定词与程度副词处理）与 snownlp 融合。
    词典完全无情感词时判为中性 —— 单纯用 snownlp 会把「会议开始，请大家汇报工作」
    判成负面（其语料偏电商评论）。三分类阈值取 0.35 / 0.65。

  4.6.5 结构化纪要
    - extract_action_items()：需要/必须/应该/要求、负责/跟进/落实、
      计划/安排、下周/近期 等**多字词**引导的句子。
      注意引导词不能写成单字字符类：旧实现用 [计划预计安排] 这种字符类，
      单个汉字（计/行/实/下）会在词中间命中，抽出
      「行卡，线上填写问卷就可以」这类碎片
    - extract_decisions()：**带主语**的结论性表态（会议/双方/一致 + 决定/同意/通过/批准）
      或无歧义动词（表决通过/审议通过）；过滤疑问句与未定表述（再决定/待定）。
      「通过」在中文里多数是「经由」之意（「通过他我了解到…」），
      把裸「通过」当决议动词会误判
    - 两者都做「重叠匹配碎片」的双向包含去重

  4.6.6 行业词汇注入分词
    register_domain_terms() 把配置的行业词表与知识库关键词注册进 jieba，
    避免「中国人寿」被切成「中国」+「人寿」导致关键词/主题出现无意义词。
    首次调用时自动注册配置词表（用独立标志位记录，不能用「已注册集合是否为空」
    当依据——调用方可能先注册了知识库关键词）。

4.7 合规比对模块（compliance_checker.py）

  4.7.1 评分权重（可通过接口修改并持久化）

    语义相似度    40 分
    必传要点覆盖  30 分
    风险识别      20 分
    关键词匹配    10 分

  4.7.2 评分等级

    ≥ 90 优秀     ≥ 75 良好     ≥ 60 合格     其余 不合格

  4.7.3 核心算法

  1. 语义相似度：对每条政策条目计算与转写文本的 bge 句向量余弦相似度，
     取最相关的一条计分（而不是求平均，避免不相关政策拉低分数）
  2. 要点模板选择：先按关键词命中数选；一个都没命中时，
     退回「与最相关政策的语义最接近」的要点模板，
     否则一份完全没提要点的会议会因模板为空而报出零遗漏
  3. 要点覆盖：逐条判定要点是否被覆盖（要点文本或同名关键词出现），
     未覆盖进入 missing_points
  4. 风险识别：风险关键词命中 + 语义风险句式；命中处用 is_negated_context()
     判断是否处于禁止/否定语境（中文「禁止/不得/不能/严禁…」与英文
     "do not / must not / never / prohibited"），否定语境不计风险；
     同一命中只计一次，避免重复扣分
  5. 时间定位：find_risk_time_markers / find_point_time_marker 返回命中句的
     起止时间，构成风险与要点的音视频时间节点
  6. 建议生成：根据总分、覆盖情况与风险数量生成改进建议
  7. 知识库字段容错：keywords / required_points 为 null、字符串或对象时，
     统一收敛为字符串列表，避免分析过程中抛异常或按字符匹配

  4.7.4 知识库条目类型

    policy / meeting_spirit                  参与语义相似度
    key_points / required                    提供必传要点与关键词
    risk_keywords / forbidden                提供风险关键词

  4.7.5 实时比对

    realtime_compliance_check(文本, 知识库, 起, 止)：实时转写每段文本调用一次，
    返回该段的 has_risk、风险关键词、覆盖要点与时间范围，
    由 Socket.IO 下发给前端当场提示。

4.8 实时转写模块（funasr_transcriber.py）

  会话对象 FunASRRealtimeTranscriber 负责：音频缓冲、断句、识别、实时合规提示、
  音频落盘与时长统计。

  关键实现点：
  1. 双通道：HTTP 接口（modules/realtime_api.py，页面使用）与 Socket.IO 事件
     （register_socketio_events，兼容第三方客户端）共享同一个转写会话类，
     业务逻辑只实现一份
  2. 采样率自适应：采集端上报实际采样率（浏览器常见 44.1k/48k），
     会话按真实采样率累计时长、计算静音阈值，识别时由引擎重采样到 16kHz；
     否则时长与时间戳会按错误比例换算（48k 当 16k 用会让时长缩到约 1/3）
  3. 时间戳推进：committed_seconds 按实际音频长度推进，而不是「识别出文字才推进」；
     旧实现在静音或识别失败时漏加时长，后续分句时间戳整体前移、与音频错位
  4. 时长统计：按累计采样点数计算，不用「块数 × 0.1」估算（浏览器定时器有抖动）
  5. 分段粒度：缓冲音频交给识别引擎自身的 VAD 切分（而不是整块当一句），
     每句都有独立起止时间，与文件级分析走同一条分段逻辑
  6. 会议标题：保存前端传入的标题（旧实现丢弃标题，回放列表里全是「实时转写会议 」）
  7. 标点：由 ct-punc 恢复（旧实现用正则给文本硬补标点，
     会在「吗/呢/吧/啊」等字后无脑加问号，把文本改坏）
  8. 空会话保护：全程没有有效语音时不写库、不留静音音频，并返回一致的空结果结构
  9. 断线/关页回收：客户端断开或关闭页面时清理会话与临时音频，避免内存与磁盘增长
 10. 事件注册：在模块导入时注册（旧实现放在 __main__ 分支里，
     用 flask run / gunicorn 等非脚本方式启动时实时功能完全不可用）

4.9 分析流水线（analysis_pipeline.py）

  把「识别 → 说话人分离 → 说话人归属 → 文本分析 → 合规比对」串成一条流程，
  供上传分析、实时转写收尾分析、第三方接口共用；支持进度回调；
  已有转写文本时跳过识别（实时转写复用），只补做说话人分离与后续分析。

4.10 会议入库模块（meeting_store.py）

  save_meeting()：一次性写入会议主体、转写分句、合规报告，并支持会议标题、
  时长、待办事项与决议结论落库。
  ensure_schema()：SQLite 下 create_all 不会给已存在的表补列，
  这里按 PRAGMA 检查并 ALTER TABLE 补齐缺失字段（幂等），使老数据库可直接升级。
  delete_meeting_files()：删除会议时清理原始音频与预处理产物。

4.11 参会统计模块（meeting_detector.py）

  count_participants() 统计参会人数；analyze_participation_distribution() 按说话人
  汇总发言时长、句数与占比。数据取自转写记录的 start_time / end_time。

4.12 文件解析模块（file_parser.py）

  解析知识库上传的政策文件（txt / pdf / docx / doc），提取标题、内容、关键词
  与必传要点，减少人工录入成本。

4.13 报表模块（report_generator.py）

  - 会议纪要报表：基本信息、参会人数与发言分布、摘要、关键词、主题、
    待办事项、决议结论、合规评分、风险关键词与遗漏要点、改进建议
  - 合规趋势报表：会议场次、平均分、分数分布、风险统计、改进建议
  所有数据在写入 HTML 前统一转义，避免注入。

七、模型体系与降级策略

7.1 设计原则

  任何模型不可用都不能导致接口不可用：每一层都有降级路径，
  且全部在本地加载，不依赖网络。

7.2 降级链路

7.2.1 语音识别
    远端 voice-api（若配置 VOICE_API_URL）→ FunASR 本地模型 → Whisper 本地模型

7.2.2 摘要生成
    Qwen2.5-1.5B-Instruct → mT5（仅当本地缓存存在）→ TextRank 抽取式摘要

7.2.3 语义相似度 / 主题分析
    本地 bge-small-zh-v1.5 → 关键词命中率 / 主题词库匹配

7.2.4 说话人分离
    pyannote 声纹模型（仅在 ENABLE_PYANNOTE=1 且模型可用时）→ 本方案（MFCC + 聚类）

7.2.5 标点
    ct-punc 标点模型 →（不可用时）保留无标点文本，不再用正则硬补

7.2.6 语音分段
    FunASR fsmn-vad → 能量 VAD（基于帧能量分位数阈值）

7.3 模型加载优化

  - 服务启动后由后台线程预热模型；端口立即可监听，页面不会因为模型加载而打不开
  - 模型单例：识别流水线、VAD、句向量模型各只加载一次
  - 首次请求若模型仍在加载，会阻塞等待（加锁 + 双重检查），不会重复加载

7.4 离线环境处理

  历史问题：text_analyzer 用 HuggingFace 仓库名（而非本地路径）加载句向量模型，
  离线环境下每次主题分析都要等 5 次重试（十几秒）后失败并降级。
  现在统一走 model_registry：本地存在则强制 local_files_only，直接读本地目录；
  mT5 备选模型同样只在本地缓存存在时才尝试加载。

十、v3.0 变更说明与后续方向

10.1 相比 v2.0 的主要变更

  识别引擎
    - 主引擎由 Whisper medium 换成 FunASR paraformer-large + ct-punc：
      实时率从远大于 1 降到约 0.1，且自带标点恢复与热词支持
    - 新增 asr_engine 统一引擎层，Whisper 转为自动兜底；新增远端 voice-api 模式

  说话人分离
    - 特征由「32ms 帧对数梅尔谱」改为「MFCC + CMVN + 1.5s 窗口池化」，
      实测分离错误率从约 24% 降到约 8.6%
    - 聚类由谱聚类/层次聚类混合改为余弦距离凝聚聚类，人数由轮廓系数自动选择
      （不再硬性偏向 3 人）
    - 说话人归属改为按时间重叠最大判定

  文本分析
    - 摘要输入改为按时间轴均匀抽样，覆盖整场会议（原来只取前 3000 字）
    - 摘要解码改为贪心，CPU 上速度提升约 3 倍
    - 新增 extract_decisions()（决议结论），与待办事项一起入库与展示
    - 情绪分析改为规则词典 + snownlp 融合，修复中性文本被误判为负面

  合规比对
    - 修复「任一关键词命中即视为全部要点已覆盖」导致遗漏事项恒为空
    - 修复风险重复计数（同一句式重复 3 次产生 9 条并重复扣分）
    - 要点模板增加语义回退选择，离题会议不再报零遗漏
    - 否定语境识别补上大小写归一化与英文否定词
    - 知识库字段异常值（null / 字符串）不再导致崩溃或按字符误匹配

  工程与稳定性
    - 新增 model_registry（离线优先、单例）与 audio_io（统一音频读写）
    - 新增 meeting_store（入库 + 表结构自愈），移除 realtime_transcriber 死代码
    - Socket.IO 事件改为导入时注册，修复非脚本启动时实时功能不可用
    - **实时转写改用 HTTP 通道**：页面原依赖 CDN 上的 socket.io 客户端，
      离线环境加载不到脚本会让「开始实时转写」点了完全没反应；现在只用浏览器原生能力
    - 实时转写修复时间戳漂移、时长估算错误、标题丢失、标点被正则改坏
    - 实时转写新增采样率自适应（48kHz 采集不再让时长缩到 1/3）
    - 修复第三方转写接口参数签名不一致必然 500
    - 修复合规自测接口调用不存在的函数必然报错
    - 修复上传分析路径把数据库访问放在应用上下文之外而必然失败
    - **修复说话人分离退化为 1 人**：预处理会改变频谱包络，而声纹特征依赖频谱包络，
      实测对预处理后音频做分离会把 2 人并成 1 人（混淆率 3.55% → 38.53%），
      改为始终对原始音频做分离；并限制小簇归并不少于 2 个说话人
    - 修复「待办事项/决议结论」把提问当任务、并从词中间截断产生碎片
      （旧实现用单字字符类当引导词，如 [计划预计安排] 会在「计」「行」处命中）
    - 修复音频质量报告 SNR 恒为 0dB（计算方法无效）并落库（此前算完即丢，
      界面上永远显示「暂无音频质量报告」）
    - 修复会议纪要报表缺少「决议结论 / 待办事项」章节
    - 修复前端多处字段错配导致永远显示 0：评分明细（components→detailed_scores）、
      情绪（positive/negative→positive_score/negative_score）、
      报表页遗漏/风险列（列表接口不返回 compliance_report，改为 include_compliance 摘要）
    - 修复报表页与知识库列表未传 page_size 而只显示最近 10 条
    - 修复页面加载即占用麦克风不释放、硬件检测异常分支渲染 undefined
    - 补上「导出会议纪要报表」入口（函数早已存在但界面无按钮）
    - 报表 HTML 全部转义
    - requirements.txt 重写为与实测环境一致（原来缺 funasr 等 7 个包，
      并 pin 了与运行环境冲突的版本）
    - 新增一键启动器（启动.bat + launcher.py）与量化评测脚本
    - .bat 脚本改为纯 ASCII：cmd 无法可靠解析 UTF-8 批处理，
      中文会让解析错位并报「不是内部或外部命令」

10.2 已知限制

  1. 说话人编号在实时转写过程中统一显示 SPEAKER_00，停止后由完整分析给出
     （在线说话人聚类需要更复杂的增量聚类策略）
  2. 说话人分离在音色接近的说话人之间仍有边界抖动（2 人场景实测 3.55%）
  3. 摘要生成在 CPU 上仍需数十秒；可用更小模型或量化进一步加速
  4. 无公开中文会议标注集，当前指标基于自建合成测试集，
     真实录音效果需按实际场景再评估

10.3 后续方向

  1. 说话人分离：引入中文声纹模型（如 CAM++ / ECAPA-TDNN）替代手工声学特征，
     并可把说话人向量与视觉信息结合（对应需求中融合视觉信息的思路）
  2. 识别纠错：结合会议主题与 PPT 文字构建更强热词表，对低置信度词做加权修正
  3. 摘要加速：int8 量化或更小模型，或流式生成
  4. 并发与部署：引入任务队列支持批量分析；容器化部署
  5. 前端：重构为组件化框架，提升交互体验
