检验日期：2026-10-08
检验范围：音频分析功能、合规比对功能（不含视频/图像识别）
检验方式：脚本化量化评测 + 接口冒烟测试，可复现
复现命令：

一、量化指标达成情况

1.1 语音转写准确率（需求指标：WER < 10%）

  测试方法：用 tests/make_ground_truth_audio.py 合成带精确文本标注的多人会议音频
  （Windows 语音合成，含 3 人会议与 2 人对话两个场景），
  用 tests/test_voice_pipeline.py 计算字错误率 CER（编辑距离 / 参考字数，忽略标点）。
  测的是**用户实际走的链路**：自适应预处理 → 识别（带热词）。

  场景                音频时长    字错误率 CER    实时率 RTF    识别引擎
  3 人会议            66.8 s      4.04%           0.79          FunASR paraformer-large
  2 人对话            44.0 s      3.42%           0.11          FunASR paraformer-large

  结论：✅ 达成。两个字错误率均低于 10% 的指标要求。
  说明：
  - RTF 含首次加载模型耗时；模型常驻后单次识别实时率约 0.1，即 10 秒音频约 1 秒识别完。
  - 同一批音频在早期实现的一刀切预处理下 CER 为 8.59% / 23.29%（预处理把清音辅音削掉），
    改为按信噪比自适应后降到 4.04% / 3.42%，比不处理（4.55% / 4.11%）还好。
  - 真实电话录音的识别错误主要来自发音含糊处，非引擎问题：同一段音频用 Whisper 交叉验证，
    FunASR 识别「中国人寿」正确而 Whisper 给出「中国人受」，Whisper 还错在
    「对接→对借」「在吗→在马」「查漏补缺→茶漏补缺」等更多处。

1.1b 伪语音片段过滤

  测试方法：真实电话录音中 VAD 会把呼吸/碰麦声当成语音，识别出「有二十。」「I.」这类
  不存在的句子。改为按「相对能量 < 语音片段中位数 45% 且时长 < 1.5 秒」丢弃这类片段。

  实测：4 个样本中真实语音片段的相对能量在 0.60~1.89 之间，
  被误判的伪语音片段为 0.41；按新判据两个真实录音里的幻觉片段（相对能量 0.0033 / 0.0155）
  均被正确丢弃，16 段真实语音一段未误杀。

1.2 说话人日志混淆率（需求指标：< 5%）

  测试方法：同一批带精确说话人与时间边界标注的音频，
  用 modules/speaker_diarization.py 的 evaluate() 做最优说话人映射后逐帧统计混淆率
  （10ms 粒度，匈牙利算法求标签最优置换）。

  场景        真实人数    识别人数    说话人混淆率    人数误差
  3 人会议    3           3           0.00%           0
  2 人对话    2           2           3.55%           0

  结论：✅ 达成。两个场景混淆率均低于 5%，且说话人数量估计完全正确。

1.3 「谁在什么时候说了什么」的说话人归属正确率

  测试方法：把识别分句按「时间重叠最大」原则归属到说话人时间段，
  再与标注的真实说话人逐句比对。

  结果：✅ 18/18 句全部正确，正确率 100.0%

1.4 音频预处理效果

  测试方法：对真实会议音频做降噪 + 带通 + 语音增强 + 归一化，
  用基于噪声底（最低能量 10% 帧）估计的信噪比对比处理前后。

  结果：✅ 降噪量 44.51 dB；信噪比 34.43 dB → 67.23 dB，改善 32.8 dB


二、音频分析功能检验

功能1：语音转写为文字（实时 + 离线文件）
检验结果：✅ 已实现
检验依据：
- modules/asr_engine.py：统一识别引擎，FunASR paraformer-large + ct-punc 标点恢复；
  FunASR 不可用时自动降级到 Whisper，两条链路返回结构一致
- 识别粒度与语音分段一致（fsmn-vad 细粒度分段），每句都有独立起止时间
- 支持热词增强（hotword），可提升行业术语与专有名词识别率
- 实时链路：modules/funasr_transcriber.py，Socket.IO 流式推送，边录边出文字
- 量化证据：见 1.1，字错误率 4.55% / 4.79%
- 接口冒烟：POST /api/v1/transcribe 返回 200，返回 18 个分句

功能2：多人会议说话人分离
检验结果：✅ 已实现
检验依据：
- modules/speaker_diarization.py：倒谱声纹嵌入（MFCC 1–19 阶 + 一阶/二阶差分，
  CMVN 归一化）→ 1.5 秒窗口池化（0.5 秒步长，L2 归一化）→ 余弦距离凝聚层次聚类
  → 轮廓系数自动选择说话人数量 → 小簇归并 / 中值滤波 / 碎段吸收
  → 按首次发言顺序编号 SPEAKER_00、SPEAKER_01……
- 不依赖麦克风阵列，不需要预先知道人数
- 量化证据：见 1.2 / 1.3，混淆率 0.00% 与 3.55%，人数估计全部正确
- 可选增强：配置 ENABLE_PYANNOTE=1 且提供 HF_TOKEN 时改用 pyannote 声纹模型
  （默认关闭：离线环境下其模型无法下载）

功能3：音频降噪、回声消除与语音增强
检验结果：✅ 已实现
检验依据：
- modules/audio_preprocessor.py：
    降噪         —— noisereduce 谱减法，失败时降级到自实现谱减法

- 每条会议都会先做预处理再识别（不再与说话人分离开关绑定）
- 量化证据：见 1.4

功能10：语义相似度比对（不止关键词匹配）
检验结果：✅ 已实现
检验依据：compliance_checker.compute_semantic_similarity() 使用本地
bge-small-zh-v1.5 句向量余弦相似度；与关键词命中（权重 10 分）分开计分，
语义相似度单独占 40 分

功能11：必传要点逐条核查与遗漏识别
检验结果：✅ 已实现
检验依据：对选定的必传要点模板逐条判定是否被覆盖（要点自身文本或同名关键词出现即视为覆盖），
未被覆盖的要点进入 missing_points
回归测试：
  - 只覆盖 1 条要点的文本 → 覆盖 1 条、遗漏 2 条 ✅
  - 与合规完全无关的离题会议 → 遗漏全部 3 条 ✅
说明：此处修复了旧实现「任一关键词命中即视为该条目全部要点都已覆盖」的缺陷，
      该缺陷会导致遗漏事项永远报 0 条、核心功能失效

功能12：0–100 分合规评分与权重配置
检验结果：✅ 已实现
检验依据：四项加权 —— 语义相似度 40 + 必传要点覆盖 30 + 风险识别 20 + 关键词命中 10，
权重可通过 GET/PUT /api/score-weights 修改并持久化；
等级划分 ≥90 优秀 / ≥75 良好 / ≥60 合格 / 其余不合格（分级测试 6/6 通过）

功能13：风险内容识别与时间节点标记

五、检验结论

语音侧需求功能全部实现并通过量化验证：
  - 转写字错误率 4.55% / 4.79%，满足 < 10% 指标
  - 说话人混淆率 0.00% / 3.55%，满足 < 5% 指标
  - 逐句说话人归属正确率 100%
  - 合规遗漏检测、风险时间节点标记、待办事项与决议结论提取均已可用

已修复的历史缺陷（摘要）：
  1. 第三方转写接口因参数签名不一致必然 500
  2. 说话人分离结果因判断条件写错而从未写回分句（全部显示 SPEAKER_00）
  3. 必传要点覆盖判定错误导致遗漏事项永远为空
  4. 风险检测重复计数导致风险分数被重复扣减
  5. 合规自测接口引用不存在的函数而必然报错
  6. 实时转写事件未注册导致用非脚本方式启动时实时功能完全不可用
  7. 实时说话人时间戳漂移、会议时长按块数估算而算错
  8. 离线环境下反复请求 HuggingFace 导致主题分析与摘要长时间等待
  9. 音频质量报告的 SNR 恒为 0dB（计算方法无效），且算完即丢、界面永远显示「暂无」
 10. 会议趋势报表在存在空分数会议时崩溃
 11. 上传分析路径把数据库访问放在应用上下文之外，勾选「合规检查」时必然失败
 12. 实时转写依赖 CDN 上的 socket.io 客户端，离线环境下点击完全无反应（已改为 HTTP 通道）
 13. 实时采集未校验采样率，48kHz 采集会让时长缩到约 1/3、时间戳错位
 14. 说话人分离误用预处理后的音频，导致 2 人会议被并成 1 人（混淆率 3.55% → 38.53%）
 15. 待办事项/决议结论把提问当任务、并从词中间截断产生碎片
     （如「行卡，线上填写问卷就可以」），且「我考虑一下再决定」被误判为决议
 16. 前端多处字段错配导致界面永远显示 0：评分明细四项、情绪正负面词数、
     报表页的遗漏要点/风险内容列（列表接口不返回合规报告）
 17. 报表页与知识库列表未传分页参数，只显示最近 10 条且无提示
 18. 会议纪要报表缺少「决议结论 / 待办事项」章节
 19. 「导出会议纪要报表」功能早已实现但界面上没有入口，用户点不到
 20. 页面加载即占用麦克风且从不释放；编辑弹窗用 style.display 而非 .show 类导致不弹窗居中
 21. **一刀切预处理把识别准确率拉低**：干净音频也跑降噪+增强，2 人对话 CER 从 4.11% 恶化到
     23.29%。改为按估计信噪比自适应（≥20dB 走轻度、<20dB 才降噪），降到 4.04% / 3.42%
 22. **热词增强是死代码**：默认热词表定义后从未被使用，知识库关键词也没喂给识别引擎。
     现在热词表 = 配置行业词汇 + 知识库关键词，三条链路都会带上
 23. **单说话人录音被拆成 2 人**：小簇归并曾设「至少保留 2 人」的下限，导致单侧通话里
     打招呼那一句被切成"另一个说话人"。改为按碎片簇形态判据（≤2 窗口 / <2.5s / 单连续段）归并
 24. **VAD 误判的噪声片段产生幻觉文本**：出现「有二十。」「I.」这类不存在的句子，
     现按「相对能量 < 45% 且时长 < 1.5s」丢弃
 25. **正确的摘要被幻觉检测误杀**：一段 166 字通话的 Qwen 摘要完全正确
     （「小王向李总介绍自己，并表示之前王总推荐其与李总对接家庭保险事宜…」），
     但摘要里 3 字以上实体只有 3 个且都不在原文，ratio 冲到 1.0 被判为幻觉，
     退回粗糙的原句拼接。现要求该类实体不少于 8 个才做比例判断
 26. **第三人称改写产生错句**：裸代词无条件全局替换，把
     「咱们这个方案还是比较实在的」改成「**参会人员**这个方案还是比较实在的」、
     「他之前在我这边配置了」改成「他之前在**发言者**这边配置了」。
     现只做短语级替换（「我认为」→「有观点认为」），落单代词保留原话
 27. **不相关的必传要点模板导致误判**：知识库里只有「项目例会要点」时，
     一通保险销售电话被判成「不合格 + 遗漏进度汇报/问题讨论/下周计划/风险说明」。
     现按「转写文本 ↔ 模板」语义相关性门控（阈值 0.50），
     不相关则明确提示「未匹配到适用的模板，建议按会议类型补充」
 28. **主题分析内容不匹配**：销售/客户沟通类录音被硬套到「人事安排」「客户服务」上。
     主题表补充了业务沟通类目（客户沟通/产品介绍/理赔服务/销售推广），
     实测该通话现在落在「客户沟通 0.58 / 产品介绍 0.52 / 理赔服务 0.52」
 29. **「通过」被当成决议动词**：「通过他也是了解到您平常很看重家人的健康」
     被误判为决议结论。现决议表态必须带主语（会议/双方/一致）或无歧义动词
     （表决通过/审议通过），并过滤「再决定/待定」这类未定表述
 30. **行业词被分词切碎**：「中国人寿」切成「中国」+「人寿」，导致关键词里出现
     无意义的「中国」。现将行业词表与知识库关键词注册进 jieba 词典

      本报告未做检验。
