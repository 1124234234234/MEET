一、量化指标达成情况

1.1 语音转写准确率（需求指标：WER < 10%）

  测试方法：用 tests/make_ground_truth_audio.py 合成带精确文本标注的多人会议音频
  （Windows 语音合成，含 3 人会议与 2 人对话两个场景），
  用 tests/test_voice_pipeline.py 计算字错误率 CER（编辑距离 / 参考字数，忽略标点）。
  测的是**用户实际走的链路**：自适应预处理 → 识别（带热词）。

  场景                音频时长    字错误率 CER    实时率 RTF    识别引擎
  3 人会议            66.8 s      4.04%           0.79          FunASR paraformer-large
  2 人对话            44.0 s      4.79%           0.11          FunASR paraformer-large

  结论：✅ 达成。两个字错误率均低于 10% 的指标要求。
  说明：
  - RTF 含首次加载模型耗时；模型常驻后单次识别实时率约 0.1，即 10 秒音频约 1 秒识别完。
  - 同一批音频在早期实现的一刀切预处理下 CER 为 8.59% / 23.29%（预处理把清音辅音削掉），
    改为按信噪比自适应后降到 4.04% / 4.79%，比不处理（4.55% / 4.11%）还好。
  - 真实电话录音的识别错误主要来自发音含糊处，非引擎问题：同一段音频用 Whisper 交叉验证，
    FunASR 识别「中国人寿」正确而 Whisper 给出「中国人受」，Whisper 还错在
    「对接→对借」「在吗→在马」「查漏补缺→茶漏补缺」等更多处。

1.1a 实时转写链路准确率（需求指标：WER < 10%）

  测试方法：tests/test_realtime_accuracy.py 把带标注音频按浏览器实际的分块
  （16bit PCM、每块 500ms）喂给实时转写会话（modules/funasr_transcriber.py，
  与页面走同一套代码），对最终文本算 CER。

  场景                音频时长    实时链路 CER     结论
  3 人会议            66.8 s      6.06%            达成（< 10%）
  2 人对话            44.0 s      2.05%            达成（< 10%）

  修复前的实测问题（用户反馈「实时转写不准」的那段录音）：
  - 根因是识别单元过短：固定静音阈值 0.012 在手机外放教学视频（背景音乐把
    RMS 抬到 0.06 以上）这类录音里判不出静音，0.35 秒断句把一句话切成
    0.3~1 秒的碎片，并且每个碎片单独送识别模型解码，既丢上下文又慢；
  - 同一段 30 秒录音修复前后对比：

    指标            修复前              修复后
    分句数          26 个碎片           7 句完整句子
    平均句长        1.03 s              3.88 s
    文本样例        「到右。」「空心长。」  「伸住自己的左手，掌心向上。」
    识别耗时        30.5 s              2.2 s

  - 同时修复两个连带 bug：停止时最后一句重复入库、停顿处切分后分句时间戳
    双重累加（末尾时间戳超出录音时长）；实时转写停止后改为按文件链路用整段
    录音重转写再做分析入库。

1.1b 伪语音片段过滤

  测试方法：真实电话录音中 VAD 会把呼吸/碰麦声当成语音，识别出「有二十。」「I.」这类
  不存在的句子。改为按「相对能量 < 语音片段中位数 45% 且时长 < 1.5 秒」丢弃这类片段。

  实测：4 个样本中真实语音片段的相对能量在 0.60~1.89 之间，
  被误判的伪语音片段为 0.41；按新判据两个真实录音里的幻觉片段（相对能量 0.0033 / 0.0155）
  均被正确丢弃，16 段真实语音一段未误杀。

1.2 说话人日志混淆率（需求指标：< 5%）

  测试方法：同一批带精确说话人与时间边界标注的音频，
  用 modules/speaker_diarization.py 的 evaluate() 做最优说话人映射后逐帧统计混淆率
  （10ms 粒度，匈牙利算法求标签最优置换）。

  场景        真实人数    识别人数    说话人混淆率    人数误差
  3 人会议    3           3           0.00%           0
  2 人对话    2           2           3.55%           0

  结论：✅ 达成。两个场景混淆率均低于 5%，且说话人数量估计完全正确。

1.2a 同一声线变调的多人音频（用户反馈的 3 人样本）

  测试方法：用户提供的 3 人会议音频（合成/变调，3 个人的音色在 MFCC 声纹上
  几乎相同），原实现只识别出 1 个说话人。

  根因：声纹嵌入（MFCC 统计量）对这 3 个声音的区分度低于同一人不同句子的波动，
  轮廓系数无论怎么切都给出 1 类；这不是聚类参数问题，而是特征里没有可用信息。

  修复：只在「聚类退化」（只得到 1 类，或最大簇占比 ≥90%）且窗口数 ≥150 时，
  启用音高二次判断 —— 逐 32ms 帧用 FFT 自相关估基频 F0，1.5 秒窗口取中位数，
  转成半音后做 1D k-means；要求相邻音高层间距 ≥3 半音、每层占比 ≥8% 才采纳，
  否则保持 1 人。

  实测：
  - 用户样本：识别为 3 人，发言占比 26% / 42% / 32%（修复前 1 人）
  - 三音高合成音频：3 人 ✅；单一音高：1 人（不误拆）✅
  - AR(1) 模拟的自然语调（带随机抖动）：1 人 ✅（正常语调波动不会被当成换人）
  - 短于 150 个窗口的片段：不做音高判断 ✅
  - 回归：原 3 人会议 / 2 人对话 / 两通真实单侧通话的人数与混淆率均不变

1.3 「谁在什么时候说了什么」的说话人归属正确率

  测试方法：把识别分句按「时间重叠最大」原则归属到说话人时间段，
  再与标注的真实说话人逐句比对。

  结果：✅ 18/18 句全部正确，正确率 100.0%

1.4 音频预处理效果

  测试方法：对真实会议音频做降噪 + 带通 + 语音增强 + 归一化，
  用基于噪声底（最低能量 10% 帧）估计的信噪比对比处理前后。

  结果：✅ 降噪量 44.51 dB；信噪比 34.43 dB → 67.23 dB，改善 32.8 dB

1.5 分析耗时与提速（准确率未变）

  测试方法：对 66.8 秒（一分钟）音频跑完整分析，服务日志按环节打印耗时。

  环节                        耗时        说明
  音频预处理                  0.2s
  语音识别（paraformer）      3.5s        实时率 0.05
  说话人分离                  0.2–4s
  关键词提取 / 主题分析       各 <0.05s   关键词与主题只算一次，摘要复用
  会议摘要（Qwen2.5）         27–35s      唯一瓶颈（CPU 推理 1.5B 模型）
  待办/决议 / 情绪 / 合规     各 <0.3s
  合计                        约 31–47s   旧实现首次分析要 65~90s

  本轮改进（都不改变识别结果）：
  - 启动时后台预热识别管线：旧实现只取引擎对象，paraformer 与标点模型
    在首次分析时才加载，用户第一次上传要多等 15~20 秒（实测 18.3s）
  - 关键词/主题只算一次：旧实现里 generate_summary 内部又各算一遍
    （主题分析要跑句向量模型），去掉重复后这两步都降到 <0.05s
  - 合规比对的句向量按文本缓存：同一段转写全文原先被重复编码 7~10 次
  - 摘要生成 token 上限 300 → 220（摘要最终只保留 300 字，多生成的被丢弃）
  - 长会议摘要输入上限 3000 → 1600 字（摘要本来就只留 300 字）

  摘要为什么还是 27~35 秒（实测数据）：
  - 本机 CPU 为 i7-14650HX（仅 AVX2），torch 2.12 的 bf16 矩阵乘是标量实现：
    1536×1536 矩阵乘 bf16 只有 1.4~1.7 GFLOP/s，fp32 有 269~511 GFLOP/s
    （差 158~360 倍），而 Qwen 权重在磁盘上正是 bfloat16；
  - 改 fp32 加载能让预填充快 6.5 倍、解码快 1.6 倍，但多占约 3GB：实测
    16GB 机器上服务占用升到 7.3GB、系统可用内存仅剩 287MB、负载 98%，
    触发内存压缩后摘要反而从 28.6s 变成 35.5s，因此默认不用；
    空闲内存 ≥8GB 时可设 SUMMARY_MODEL_DTYPE=float32 提速；
  - 动态 int8 量化（1.5GB、8 token/s）试过但质量明显下降
    （把合规培训会议总结成「财务报告中的风险控制」），不可用；
  - 结论：识别侧（1 分钟音频 3.5s）与其它分析环节（合计约 1s）已经没有优化空间，
    剩下的时间全部是 CPU 上 1.5B 摘要模型的推理；要再快只能换更大的内存
    （用 fp32）或换机器/加显卡，或关闭大模型摘要改用抽取式
    （ENABLE_TEXT_MODELS=false，整场分析约 5 秒，摘要是原句拼接而非改写）。


二、音频分析功能检验

功能1：语音转写为文字（实时 + 离线文件）
检验结果：✅ 已实现
检验依据：
- modules/asr_engine.py：统一识别引擎，FunASR paraformer-large + ct-punc 标点恢复；
  FunASR 不可用时自动降级到 Whisper，两条链路返回结构一致
- 识别单元：细粒度语音片段先并成「识别单元」整体解码（间隔 < 1.5s 视为同一段

  实测 30 秒录音从 24 个碎片（平均 4.9 字）变为完整句子，耗时 17.0s → 2.6s
- 支持热词增强（hotword），可提升行业术语与专有名词识别率

- 接口冒烟：POST /api/v1/transcribe 返回 200，返回 6 个分句

功能2：多人会议说话人分离
检验结果：✅ 已实现
检验依据：
- modules/speaker_diarization.py：倒谱声纹嵌入（MFCC 1–19 阶 + 一阶/二阶差分，
  CMVN 归一化）→ 1.5 秒窗口池化（0.5 秒步长，L2 归一化）→ 余弦距离凝聚层次聚类
  → 轮廓系数自动选择说话人数量 → 小簇归并 / 中值滤波 / 碎段吸收
  → 按首次发言顺序编号 SPEAKER_00、SPEAKER_01……
- 不依赖麦克风阵列，不需要预先知道人数
- 小簇归并判据：窗口数 ≤2 且跨度 <2.5s 且单连续段 且占比 <8% 才视为碎片。
  占比门槛的意义：只按前三条判，短录音里真实的「少言说话人」（例如 15 秒对话里
  第二位只说了两句）会被并掉，全场只剩 SPEAKER_00。七个样本实测：碎片簇占比
  都 ≤3.7%，真实说话人最少也有 23.6%，门槛取 8% 两边都不误伤
- 实时阶段也做说话人标注：每 15 秒音频对已录音频重跑一次离线分离算法并刷新全部分句，
  录制中即可区分 SPEAKER_00/01（1 分钟音频约 0.1~0.3 秒），不再等停止后才知道
- 音高二次判断：聚类退化（1 类或最大簇 ≥90%）且窗口 ≥150 时，按基频层级拆分
  同一音色变调的多人音频；门槛（层间距 ≥3 半音、占比 ≥8%）保证正常语调起伏不误拆，
  见 1.2a
- 量化证据：见 1.2 / 1.2a / 1.3，混淆率 0.00% 与 3.55%，人数估计全部正确；
  真实单侧通话实测判成 1 人（不误拆）；回归测试 17/17 通过
  （tests/test_speaker_recognition.py）
- 可选增强：配置 ENABLE_PYANNOTE=1 且提供 HF_TOKEN 时改用 pyannote 声纹模型
  （默认关闭：离线环境下其模型无法下载）

功能2b：会议纪要 / 会议记录概要 / 记录全文（三份文件，按日期归档，可预览、可多格式导出）
检验结果：✅ 已实现
检验依据：

  - 会议记录概要.md：时间/时长/参会人/发言规模/评分/主题/关键词/情绪/待办与决议条数的
    速览表格 + 摘要 + 待办清单 + 决议清单 + 合规与风险
  - 会议记录全文.md：按 [时间] 说话人：文本 排列的逐字记录（纪要附件）

  用户不必为措辞多等半分钟
- 待办表格：负责人（「张总负责…」「请王经理…」）与时间（本周五/下周一/月底/3 天内）
  从文字中提取；无动作词的陈述句、提问、片段（<8 字或 >60 字）一律不进表格；
  实测「完成了百分之四十，接下来…」这类叙述不再被当成待办
- 公文要素可填写：会议地点/主持人/记录人在「编辑会议信息」里填，保存后文档自动重新生成；
  未填写时显示「—」，记录人默认由系统署名

  做替换、超长标题截断、带会议 id 防同名覆盖；UTF-8 with BOM（记事本打开不乱码）

功能3：音频降噪、回声消除与语音增强
检验结果：✅ 已实现
检验依据：
- modules/audio_preprocessor.py：
    降噪         —— noisereduce 谱减法，失败时降级到自实现谱减法
    回声/噪声抑制 —— 80–7000Hz 四阶带通滤波
    语音增强     —— 基于判决引导先验信噪比的 MMSE 谱增益

五、检验结论

语音侧需求功能全部实现并通过量化验证：
  - 转写字错误率 4.04% / 4.79%（文件链路）、6.06% / 2.05%（实时链路），满足 < 10% 指标
  - 说话人混淆率 0.00% / 3.55%，满足 < 5% 指标；同声线变调的 3 人音频也能分出 3 人
  - 逐句说话人归属正确率 100%
  - 会议纪要按飞书妙记版式生成（信息表 + 摘要 + 讨论要点 + 决议 + 待办表格 + 合规风险），
    三份文档按日期归档，页面可预览，可导出 Word/PDF/Markdown/纯文本
  - 合规遗漏检测、风险时间节点标记、待办事项与决议结论提取均已可用

已修复的历史缺陷（摘要）：
  1. 第三方转写接口因参数签名不一致必然 500
  2. 说话人分离结果因判断条件写错而从未写回分句（全部显示 SPEAKER_00）
  3. 必传要点覆盖判定错误导致遗漏事项永远为空
  4. 风险检测重复计数导致风险分数被重复扣减
  5. 合规自测接口引用不存在的函数而必然报错
  6. 实时转写事件未注册导致用非脚本方式启动时实时功能完全不可用
  7. 实时说话人时间戳漂移、会议时长按块数估算而算错
  8. 离线环境下反复请求 HuggingFace 导致主题分析与摘要长时间等待
  9. 音频质量报告的 SNR 恒为 0dB（计算方法无效），且算完即丢、界面永远显示「暂无」
 10. 会议趋势报表在存在空分数会议时崩溃
 11. 上传分析路径把数据库访问放在应用上下文之外，勾选「合规检查」时必然失败
 12. 实时转写依赖 CDN 上的 socket.io 客户端，离线环境下点击完全无反应（已改为 HTTP 通道）
 13. 实时采集未校验采样率，48kHz 采集会让时长缩到约 1/3、时间戳错位
 14. 说话人分离误用预处理后的音频，导致 2 人会议被并成 1 人（混淆率 3.55% → 38.53%）
 15. 待办事项/决议结论把提问当任务、并从词中间截断产生碎片
     （如「行卡，线上填写问卷就可以」），且「我考虑一下再决定」被误判为决议
 16. 前端多处字段错配导致界面永远显示 0：评分明细四项、情绪正负面词数、
     报表页的遗漏要点/风险内容列（列表接口不返回合规报告）
 17. 报表页与知识库列表未传分页参数，只显示最近 10 条且无提示
 18. 会议纪要报表缺少「决议结论 / 待办事项」章节
 19. 「导出会议纪要报表」功能早已实现但界面上没有入口，用户点不到
 20. 页面加载即占用麦克风且从不释放；编辑弹窗用 style.display 而非 .show 类导致不弹窗居中
 21. **一刀切预处理把识别准确率拉低**：干净音频也跑降噪+增强，2 人对话 CER 从 4.11% 恶化到
     23.29%。改为按估计信噪比自适应（≥20dB 走轻度、<20dB 才降噪），降到 4.04% / 3.42%
 22. **热词增强是死代码**：默认热词表定义后从未被使用，知识库关键词也没喂给识别引擎。
     现在热词表 = 配置行业词汇 + 知识库关键词，三条链路都会带上
 23. **单说话人录音被拆成 2 人**：小簇归并曾设「至少保留 2 人」的下限，导致单侧通话里
     打招呼那一句被切成"另一个说话人"。改为按碎片簇形态判据（≤2 窗口 / <2.5s / 单连续段）归并
 24. **VAD 误判的噪声片段产生幻觉文本**：出现「有二十。」「I.」这类不存在的句子，
     现按「相对能量 < 45% 且时长 < 1.5s」丢弃
 25. **正确的摘要被幻觉检测误杀**：一段 166 字通话的 Qwen 摘要完全正确
     （「小王向李总介绍自己，并表示之前王总推荐其与李总对接家庭保险事宜…」），
     但摘要里 3 字以上实体只有 3 个且都不在原文，ratio 冲到 1.0 被判为幻觉，
     退回粗糙的原句拼接。现要求该类实体不少于 8 个才做比例判断
 26. **第三人称改写产生错句**：裸代词无条件全局替换，把
     「咱们这个方案还是比较实在的」改成「**参会人员**这个方案还是比较实在的」、
     「他之前在我这边配置了」改成「他之前在**发言者**这边配置了」。
     现只做短语级替换（「我认为」→「有观点认为」），落单代词保留原话
 27. **不相关的必传要点模板导致误判**：知识库里只有「项目例会要点」时，
     一通保险销售电话被判成「不合格 + 遗漏进度汇报/问题讨论/下周计划/风险说明」。
     现按「转写文本 ↔ 模板」语义相关性门控（阈值 0.50），
     不相关则明确提示「未匹配到适用的模板，建议按会议类型补充」
 28. **主题分析内容不匹配**：销售/客户沟通类录音被硬套到「人事安排」「客户服务」上。
     主题表补充了业务沟通类目（客户沟通/产品介绍/理赔服务/销售推广），
     实测该通话现在落在「客户沟通 0.58 / 产品介绍 0.52 / 理赔服务 0.52」
 29. **「通过」被当成决议动词**：「通过他也是了解到您平常很看重家人的健康」
     被误判为决议结论。现决议表态必须带主语（会议/双方/一致）或无歧义动词
     （表决通过/审议通过），并过滤「再决定/待定」这类未定表述
 30. **行业词被分词切碎**：「中国人寿」切成「中国」+「人寿」，导致关键词里出现
     无意义的「中国」。现将行业词表与知识库关键词注册进 jieba 词典
 31. **实时转写「不准」（用户反馈的那段录音）**：固定静音阈值 0.012 在手机外放
     教学视频（背景音乐把 RMS 抬到 0.06 以上）这类录音里判不出静音，0.35 秒断句
     把一句话切成 0.3~1 秒碎片，且每个碎片单独送模型解码。同一段 30 秒录音：
     26 个碎片（平均 1.03s，「到右。」「空心长。」）→ 7 句完整句子（平均 3.88s），
     识别耗时 30.5s → 2.2s；实时链路 CER 实测 6.06% / 2.05%
 32. **识别单元过短**（文件链路同样受益）：VAD 把一句话内部的换气也切成片段，
     逐片识别丢上下文。现先并成识别单元整体解码，再把文本按片段比例还原成
     带时间戳的分句（只在句末标点处断开），实测 CER 6.16% → 4.11%、耗时降到 1/6
 33. **实时转写停止时最后一句重复入库**：get_final_result 把已经计入历史的尾块
     文本又拼了一遍，导致 44 秒对话识别出 163 字（参考 146 字）
 34. **停顿处切分后分句时间戳双重累加**：偏移量在识别后才推进，末尾时间戳
     超出录音时长（实测 47.77s / 录音 44.0s）。改为识别前取值，并加测试卡住双向误差
 35. **实时转写落库用的是边说边出的碎片文本**：现在停止后按文件链路用整段录音
     重新识别一遍再做分析入库（实时文本只用于现场展示），重转写失败才退回实时文本
 36. **同一声线变调的 3 人音频只识别出 1 人**（用户反馈）：3 个声音的 MFCC 声纹
     区分度低于同一人不同句子的波动，轮廓系数恒为 1 类。现对退化结果启用音高
     二次判断（逐帧 F0 → 半音 1D k-means，要求层间距 ≥3 半音、占比 ≥8%、
     窗口 ≥150），该音频现识别为 3 人（26% / 42% / 32%）；单音高、自然语调抖动、
     短片段均不误拆，原有 4 个场景结果不变
 37. **纪要照抄转写原句**（用户反馈「这纪要不行」）：旧实现把分句直接加
     「会议认为/会议强调」引导语，产出「会议认为，先请理工作一下技术这边的情况」
     这类半文半白的句子。现改为飞书妙记式结构：规则层删应声/称呼/客套
     （「好的，张总，…」）、人称规范化（我/您 → 我方/对方）、压成 60 字内要点；
     模型层只负责改写成 15~40 字短语，逐条过保真校验，改错即退回
 38. **纪要出现「1. 1. 会议听取了，…」重复编号**：数据库缓存的 minutes_body
     带着上一版编号与引导语，新 writer 又加一次。现在 writer 统一剥除行首编号和
     引导语，并清理全部历史缓存后重新生成（89 场）
 39. **待办表格里全是叙述句**：摘要里的「完成了百分之四十，接下来…」被当成待办，
     负责人/时间两列全是「—」。现要求必须含动作动词（负责/提交/落实/安排…）、
     长度 8~60 字、不是提问、不以「完成/目前/大概」开头，否则不进表格
 40. **会议文档页信息挤成一团、只能下载 .md**（用户反馈）：三份文件各占一大块，
     路径与按钮混排；下载链接写死 .md。现改为每份文件一行
     「图标 + 名称 + 说明 + 预览/下载」，下载弹出格式选择（Word/PDF/Markdown/纯文本），
     后端按 format 参数即时转换（docx/pdf/txt），导出文件与 .md 同目录
 41. **文档预览把信息行压成一段**：「会议时间 | 会议地点 | …」在预览里连成一行。
     现前端 Markdown 渲染按行 `<br>` 保留换行，docx 每条加软换行、pdf 转 `<br/>`，
     预览与导出文档的版式一致
 42. **导出的有序列表编号跨章节连续**：txt 用「已有缩进行数 + 1」当序号，摘要的
     第 1 条显示成 2、讨论要点从 4 编到 11；Word 的 List Number 样式同样跨章节
     累加。现按 Markdown 里的原始序号渲染，每个章节各自从 1 开始
 43. **讨论要点里混进提问与关键词罗列**：「……压力测试结果怎么样」「有没有完成」
     和「涉及的关键内容：完成、自动、版本…」都进了纪要。现剔除疑问句，删除关键词
     罗列条目（会议议题里已有）；同时把口语数字写成书面形式（65%、1.2 秒、V2.0）

      本报告未做检验。
